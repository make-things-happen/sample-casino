Generate a weekly changelog for stakeholders — summarizes recent product changes in plain, non-technical language using Discord markdown format.

## Input

This command accepts an optional **start date** argument via `$ARGUMENTS` in `YYYY-MM-DD` format.

- If `$ARGUMENTS` contains a date, use it as the start of the changelog period.
- If `$ARGUMENTS` is empty, default to **Monday of the current week** (most recent Monday at 00:00).

The end date is always **now** (the current date and time).

## Workflow

### Step 1: Determine the date range

Calculate the start date:
- If the user provided a date, use it directly.
- Otherwise, compute Monday of the current week:
  ```bash
  date -d "last monday" +%Y-%m-%d 2>/dev/null || date -dlast-monday +%Y-%m-%d
  ```

Confirm the date range to yourself before proceeding (e.g., "Changelog from 2026-02-09 to 2026-02-12").

### Step 2: Gather all changes

Run these commands to collect raw change data:

```bash
# All commits in the date range across all branches merged into dev/master/staging
git log --all --merges --since="<start_date>" --pretty=format:"%h|%s|%b" --no-decorate

# All commits (including non-merge) for completeness
git log --all --since="<start_date>" --pretty=format:"%h|%s|%b" --no-decorate

# List of all files changed in the period
git log --all --since="<start_date>" --name-only --pretty=format:"" | sort -u

# PR titles merged in the period (if gh is available)
gh pr list --state merged --search "merged:>=$(start_date)" --json title,mergedAt,number,labels --limit 100
```

### Step 3: Analyze and categorize changes

Review all commits, PR titles, and changed files. Categorize every meaningful change into one of these stakeholder-friendly buckets:

1. **New Features** — entirely new capabilities or pages added to the product
2. **Improvements** — enhancements to existing functionality (better UX, faster performance, smarter defaults)
3. **Bug Fixes** — issues that were broken and are now fixed
4. **Operational / Infrastructure** — changes that improve reliability, security, or deployment (only include if they have user-visible impact or are significant enough for stakeholders to care about, e.g., "improved system reliability" or "faster page loads")

**Filtering rules — what to INCLUDE and EXCLUDE:**

- INCLUDE: UI changes, new pages/dashboards, new reports, workflow changes, new integrations, data/analytics improvements, permission/role changes, financial logic changes, payout changes, offer management changes, tracking improvements.
- EXCLUDE: Pure code refactors with no user-visible impact, dependency updates, linter/formatter changes, CI config tweaks, test additions, internal tooling changes, developer experience improvements, file renames with no functional change.
- When in doubt, ask yourself: "Would a non-technical stakeholder or investor care about this?" If no, skip it.

### Step 4: Write the changelog

Write the changelog using **Discord markdown format** with the following structure. The tone should be professional, pragmatic, direct, and non-technical. No filler words, no hype, no embellishment. State what changed and move on.

**Format template:**

```
# Changelog: <Start Date> — <End Date>

> One-line summary of what shipped.

## New Features
- **<Feature name>** — <What it does, one sentence>
- ...

## Improvements
- **<Area>** — <What changed>
- ...

## Bug Fixes
- **<What was fixed>** — <What broke and that it's resolved>
- ...

## Infrastructure & Reliability
- **<Change>** — <Impact in plain terms>
- ...

-# This changelog was generated by <model>.
```

**Writing rules:**

1. **No technical jargon.** Never mention: API, tRPC, Drizzle, schema, migration, component, endpoint, middleware, hook, state, refactor, merge, rebase, deploy pipeline, CI/CD, linter, TypeScript, SQL, query, mutation, cache, Redis, Neon, Vercel, or similar. Translate into business/product language.
2. **No flavor.** Do not use words like "powerful", "seamless", "robust", "exciting", "comprehensive", "packed", "smarter", "deeper", "sleek", "cutting-edge", or any similar marketing language. Just say what it does.
3. **Lead with what changed.** Instead of "Added a new tRPC router for payouts", write "Operators can now view and manage payouts from their dashboard."
4. **Be specific and short.** Each bullet is 1 sentence max. Name the page or workflow affected.
5. **Active voice.** "Affiliates can now..." not "A feature was added that allows..."
6. **Group related commits.** Multiple commits delivering one feature = one bullet point.
7. **Omit empty sections.** If there are no bug fixes, don't include the Bug Fixes heading.
8. **The summary line** (blockquote at the top) should be 1 sentence, factual (e.g., "Shipped affiliate marketplace and operator activity log.").
9. **Date format** in the heading should be human-friendly: `Feb 9, 2026 — Feb 12, 2026`.
10. **Disclaimer.** Always end with `-# This changelog was generated by <model>.` where `<model>` is replaced by the actual model name/ID you are running as. Use Discord's subtext format.

### Step 5: Present to the user

Output the full changelog in a single code block so the user can copy-paste it directly into Discord:

````
```md
# Changelog: Feb 9, 2026 — Feb 12, 2026
...
```
````

Then, outside the code block, briefly mention:
- How many commits/PRs were analyzed
- How many were excluded as internal/technical-only
- Offer to adjust tone, add/remove items, or change the date range

## Important Rules

- **This is NOT a git log dump.** Never list commit hashes, branch names, or raw commit messages in the output.
- **Never expose internal architecture.** The reader should have zero idea what tech stack is used.
- **Accuracy matters.** Do not invent or embellish changes. Every bullet must trace back to actual commits or PRs in the period.
- **When the period is quiet**, say so honestly. A short changelog is better than a padded one. Write: "A lighter week focused on stability and internal improvements." rather than inflating minor changes.
- **If zero user-facing changes exist**, output a brief note: "No user-facing changes were shipped this period. The team focused on internal improvements and stability work."
